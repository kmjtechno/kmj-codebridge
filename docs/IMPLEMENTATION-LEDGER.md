- `src/jobs.js` deliberately left untouched — `redact()`'s byte-for-byte semantics (label/separator preserved, only the bare value masked) are unchanged and provably so, since nothing in that file was edited.
- Applied as a single atomic `write_files_atomic` call from a verified clean `origin/main` baseline, so the working tree was never left in an uncompilable intermediate state (the previous attempt had self-locked on its own comment text tripping the then-active whole-file check; this time the baseline was re-verified clean before writing and the new code's own comments were checked against the new binding scan before being committed).

## Performance/low-load design pass (2026-10-02, design only — no agent.js/gateway.js changes)

- Re-read `src/gateway.js`/`src/agent.js` end to end before proposing any redesign. Finding: the gateway's `/agent/poll` path is already an event-driven long-poll — `forward()` enqueues a job and calls a stored `wake()` resolver immediately if the target agent has an open poll; there is no DB/storage polling loop. Wake latency for real work is already ~0ms.
- Ruling: do not introduce a new persistent-socket protocol (the brief's option B). The existing long-poll design already meets the stated idle/wake goals; a new transport would add a second connection-lifecycle model to secure and test for an unmeasured, likely-small benefit. Cost if wrong: idle network chatter stays somewhat higher than a socket-based design would allow — recoverable later, smaller risk than shipping a new transport unverified.
- Actual bug found: `src/agent.js`'s loop applies `delay(Math.min(10000, pollMs * 2**failures))` unconditionally after every iteration, including a clean success. This is a small idle cost (≤250ms default tacked onto a ~10s cycle) but a real **active-path** cost — every tool dispatch pays an extra `pollMs` before the agent re-polls. Smallest safe fix (not yet applied, pending agent.js authorization): only delay/backoff after an actual request failure; loop straight back into `/agent/poll` after a clean cycle.
- `renew()` is already deadline-driven (checks `Date.now() < nextRenewal` and returns early) — the brief's Phase 5 target is already met; no redesign needed there.
- `markConnected()` already debounces `connection.json` writes to at most once per 30s, but by wall-clock time rather than connection-state transition. Raising the gateway long-poll timeout from 10s toward 45-60s (new bounded `pollWaitMs` config field, consistent with how `pollMs`/`deviceTimeoutMs` are already exposed) directly reduces this write frequency further and cannot add latency to real work, since wake is event-driven, not timeout-driven.
- Full design, including the Phase 6 `project_snapshot` candidate schema, the Phase 7 Supervisor allowlist/IPC sketch and the Phase 8 self-update/rollback flow, written up in `docs/PERFORMANCE-ARCHITECTURE.md`. A bounded, single-shot benchmark harness (`scripts/benchmark.js`, Linux `/proc`-based idle sampling + direct dispatcher latency timing, JSON output) was added so the baseline/after-comparison in the brief's Phase 14 can be run and compared without guessing.
- Not done: no idle CPU/RSS/disk/network numbers have actually been captured yet (needs the user to run `scripts/benchmark.js` on the VPS, or grant process-level access from this session). No agent.js/gateway.js/config.js change has been made — this entire section is read-only inspection plus prepared design, per the explicit instruction not to touch agent.js until the sensitive-binding patch is proven green.

This repository commits no hosted gateway domain by design (every doc uses `YOUR-ACTUAL-HOST`), so the icon Claude.ai shows for a self-hosted operator's connector is controlled by whatever favicon that operator's chosen domain serves — outside this repository's control. Runtime extraction requires one exact signed release root, rejects traversal/backslash/duplicate/symlink/hardlink/special entries, extracts with `tar` without a shell or owner/permission restoration, and revalidates the resulting tree. The RED suite failed before these APIs existed; the full GREEN test suite passed after implementation.
- Update orchestration was then developed test-first in `src/update-orchestrator.js`: verified prepare composes signed-manifest verification, download/extraction, cleanup, an explicit successful preflight hook, and immutable finalization; activation uses bounded health retries and automatically rolls back/restarts the previous known-good release if restart or health verification fails. Rollback-operation, rollback-restart and rollback-health failures are distinct fail-closed states. The initial RED run proved the module was absent, a fixture-only non-hex release identity was corrected without weakening production validation, and the hardening RED/GREEN cycle added preflight plus structured rollback failure coverage. Production self-update remains gated on fixed Supervisor RPC wiring, real manifest/signature/key custody configuration, concrete preflight, authenticated agent/gateway health probes and a live fault-injection rollback drill on the immutable runtime layout.
